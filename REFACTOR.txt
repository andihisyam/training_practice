````markdown
# Refactor Metodologi Eksperimen T2DM Classification

## Tujuan

Refactor pipeline penelitian agar metodologi eksperimen lebih bersih, reproducible,
mudah dipertanggungjawabkan secara akademik, dan sesuai dengan tujuan penelitian.

Penelitian ini difokuskan pada:

> Klasifikasi status Diabetes Mellitus Tipe 2 (T2DM) berdasarkan karakteristik
> demografis dan klinis pasien dari Electronic Health Record (EHR).

Penelitian **bukan** ditujukan untuk memprediksi apakah pasien akan mengalami
T2DM pada masa depan.

Target tetap:

```text
DMIndicator
0 = Non-DM
1 = DM
````

Konteks penggunaan model adalah **screening/identifikasi status T2DM**, sehingga
Sensitivity/Recall merupakan metric klinis yang penting.

Namun pemilihan algoritma tidak boleh hanya berdasarkan Recall, karena model yang
memprediksi seluruh pasien sebagai DM dapat menghasilkan Recall 100%.

Primary metric untuk model selection:

```text
PR-AUC / Average Precision
```

Clinical priority metric:

```text
Recall / Sensitivity
```

---

# 1. Prinsip Utama Refactor

Pipeline lama jangan dihapus.

Hasil lama harus dianggap sebagai:

```text
Preliminary / Exploratory Experiments
```

Bukan:

```text
Final Experimental Results
```

Pipeline baru harus memisahkan dengan jelas:

```text
DEVELOPMENT DATA
vs
FINAL LOCKED TEST DATA
```

Semua keputusan berikut WAJIB dilakukan hanya menggunakan development data:

* feature set selection
* model comparison
* imbalance strategy selection
* hyperparameter tuning
* threshold tuning

Final test hanya boleh digunakan setelah semua keputusan di atas sudah selesai.

---

# 2. Framing Penelitian

Gunakan framing:

> Binary classification of T2DM status based on demographic and clinical EHR
> characteristics.

Jangan menggunakan framing:

```text
future diabetes prediction
future T2DM risk
will develop diabetes
prediksi pasien akan terkena DM
prediksi kejadian T2DM di masa depan
```

Alasannya:

Dataset tidak menyediakan timestamp diagnosis pertama T2DM yang cukup jelas untuk
membentuk prediction window / observation window temporal.

Model hanya mengetahui:

```text
DMIndicator = 0 / 1
```

sebagai status pasien.

# 3. Fitur yang Harus Dikeluarkan dari Primary Model

## 3.1 Physician Specialty

Drop seluruh fitur:

```text
PhySp_*
```

Contoh:

```text
PhySp_Internal_Medicine
PhySp_General_Practice
PhySp_*
```

### Alasan

Physician Specialty berpotensi menjadi proxy terhadap status penyakit.

Contoh shortcut:

```text
Pasien sudah DM
    ↓
lebih sering berkunjung ke Internal Medicine
    ↓
model melihat specialty
    ↓
model memprediksi DM
```

Karena kita tidak memiliki tanggal onset DM pertama yang dapat digunakan sebagai
temporal cutoff, tidak dapat dipastikan apakah specialty muncul sebelum atau setelah
pasien diketahui menderita DM.

Primary model harus berfokus pada karakteristik pasien, bukan care pathway.

---

## 3.2 State

Drop seluruh fitur:

```text
State_*
```

dan source column:

```text
State
```

### Alasan

State dapat menjadi proxy terhadap:

* lokasi geografis
* practice tertentu
* perbedaan populasi
* perbedaan prevalensi
* pola pencatatan EHR
* karakteristik fasilitas kesehatan

Model utama tidak boleh bergantung pada lokasi pasien.

---

## 3.3 PracticeGuid

Jangan gunakan:

```text
PracticeGuid
```

sebagai predictor.

Tetapi JANGAN hapus permanen dari intermediate dataset.

Gunakan hanya sebagai metadata.

Potential future use:

```python
GroupKFold(groups=PracticeGuid)
```

atau analisis generalisasi antar-practice.

## 3.4 Diagnosis / ICD

Diagnosis tidak boleh menjadi predictor primary model.

Drop feature family yang berasal dari:

```text
diagnosis
ICD
Dx_*
Diag_*
```

atau nama lain yang setara dalam pipeline saat ini.

### Alasan

Diagnosis terlalu dekat dengan outcome dan berisiko menjadi target proxy / leakage.

Diagnosis boleh tetap digunakan sebagai:

```text
leakage comparator
sensitivity analysis
exploratory experiment
```

tetapi bukan primary model.

---

## 3.5 Medication

Medication tidak boleh menjadi predictor primary model.

Drop seluruh feature family medication.

### Alasan

Obat tertentu dapat langsung mengindikasikan kondisi DM.

Contoh:

```text

    ↓
```

Ini merupakan shortcut yang terlalu dekat dengan target.

# 8. Height Features

Drop dari primary model:

```text
Height_Min
Height_Max
Height_Mean
Height_NObs
Height_Change
```

atau seluruh:

```text
Height_*
```

### Alasan

Untuk pasien dewasa, tinggi badan relatif stabil.

Perubahan tinggi longitudinal lebih mungkin merepresentasikan:

* measurement variation
* data entry differences
* unit inconsistency
* measurement noise

Selain itu BMI sudah merepresentasikan hubungan antara Weight dan Height.

Primary model tidak perlu menggunakan Height secara terpisah.

# 9. Weight Features

Jangan masukkan Weight ke primary model terlebih dahulu.

Feature family:

```text
Weight_*
```

harus tersedia hanya untuk eksperimen tambahan.

### Alasan

BMI secara matematis sudah membawa informasi Weight:

```text
BMI = Weight / Height²
```

Sehingga:

```text
BMI_Mean
Weight_Mean
```

berpotensi membawa informasi yang redundant.

Namun jangan menyimpulkan Weight tidak berguna tanpa eksperimen.

Buat feature experiment khusus:

```text
Primary Clinical Set
vs
Primary Clinical Set + Weight
```

Contoh candidate tambahan:

```text
Weight_Mean
Weight_Max
```

Jika penambahan Weight memberikan improvement yang sangat kecil, prioritaskan model
tanpa Weight berdasarkan prinsip parsimony.

---

# 10. Change Features

Untuk primary model, DROP semua feature:

```text
*_Change
```

Contoh:

```text
BMI_Change
Weight_Change
SystolicBP_Change
DiastolicBP_Change
Temperature_Change
RespiratoryRate_Change
Height_Change
```

### Masalah metodologis

Implementasi Change saat ini pada dasarnya:

```text
mean(last year) - mean(first year)
```

Masalahnya observation period tiap patient tidak sama.

Contoh:

```text
Patient A
2009 BMI = 25
2012 BMI = 30

Change = +5 dalam 3 tahun
```

vs

```text
Patient B
2011 BMI = 25
2012 BMI = 30

Change = +5 dalam 1 tahun
```

Current `Change` memberikan value yang sama:

```text
+5
```

padahal rate of change berbeda.

Masalah lain:

Jika patient hanya memiliki data satu tahun:

```text
first year = last year
```

maka:

```text
Change = 0
```

Padahal `0` bisa berarti:

```text
benar-benar stabil
```

atau:

```text
hanya punya satu tahun observasi
```

Dua kondisi tersebut berbeda.

### Future improvement

Jika ingin menggunakan longitudinal change, buat feature baru:

```text
*_SlopePerYear
```

Contoh:

```python
slope = (last_value - first_value) / (last_year - first_year)
```

Hanya hitung apabila:

```text
last_year > first_year
```

dan pasien memiliki minimal dua observation year berbeda.

Jangan implementasikan slope dalam primary refactor kecuali diminta secara eksplisit.

# 16. Feature Set Selection Rule

Feature set selection dilakukan HANYA menggunakan:

```text
70% Development Data
```

dengan:

```text
Stratified 5-Fold Cross Validation
```

Jangan menggunakan final test.

Metric utama:

```text
mean PR-AUC
```

Metric tambahan:

```text
std PR-AUC
Recall
Precision
F1
ROC-AUC
```

Selection rule:

Jika feature set kompleks hanya memberikan improvement yang sangat kecil dibanding
feature set sederhana, pilih feature set sederhana.

Contoh:

```text
Set B
PR-AUC = 0.468 ± 0.018

Set D
PR-AUC = 0.472 ± 0.025
```

Selisih:

```text
0.004
```

Jika improvement kecil dibanding variability antar-fold, prioritaskan Set B.

Prinsip:

```text
PARSimony:
jika performa hampir sama, pilih model/feature set yang lebih sederhana.
```

Jangan memilih feature set hanya karena mean PR-AUC terbesar secara numerik jika
selisihnya sangat kecil.

# 21. Primary Metric Model Selection

Primary metric:

```text
PR-AUC / Average Precision
```

Reason:

Dataset memiliki class imbalance dan target positif DM merupakan kelas yang lebih
sedikit.

PR-AUC lebih informatif daripada Accuracy untuk evaluasi positive class.

Secondary metrics:

```text
Recall / Sensitivity
Precision
F1
ROC-AUC
Specificity
```

Untuk model selection:

1. prioritaskan mean PR-AUC
2. lihat stability antar-fold
3. lihat Recall karena konteks screening
4. hindari memilih model dengan Recall tinggi tetapi Precision/Specificity sangat buruk

---

# 22. Imbalance Strategy Experiment

Setelah algoritma kandidat terbaik ditemukan, lakukan eksperimen imbalance.

Bandingkan minimal:

## Condition A — Baseline

```text
SMOTE = OFF
Class Weight = OFF
```

## Condition B — Class Weight

```text
SMOTE = OFF
Class Weight = ON
```

## Condition C — SMOTE

```text
SMOTE = ON
Class Weight = OFF
```

Optional:

## Condition D — SMOTE + Weight

```text
SMOTE = ON
Class Weight = ON
```

Condition D hanya boleh ada jika sengaja diuji sebagai kombinasi.

Jangan tanpa sengaja membuat:

```text
SMOTE experiment
```

tetapi model masih mempunyai:

```text
scale_pos_weight
class_weight
```

aktif.

# 23. SMOTE Requirement

Jika menggunakan SMOTE:

SMOTE HANYA boleh dilakukan pada training fold.

Benar:

```text
CV fold:

Train Fold
    ↓
Preprocessing
    ↓
SMOTE
    ↓
Model fit

Validation Fold
    ↓
NO SMOTE
    ↓
Evaluation
```

Salah:

```text
SMOTE seluruh dataset
    ↓
CV
```

Gunakan `imblearn.pipeline.Pipeline` jika diperlukan agar SMOTE terjadi di dalam
cross-validation secara benar.

# 27. Threshold Selection Principle

Jangan menggunakan:

```text
sort by F1 only
```

karena konteks screening menekankan sensitivity.

Recommended strategy:

Gunakan salah satu dari:

```text
maximize F2-score
```

atau:

```text
maintain high Recall
while maximizing Specificity / Precision
```

Jika ada target clinically justified, misalnya:

```text
Recall >= X%
```

gunakan target tersebut.

Tetapi jangan hard-code Recall target tanpa dokumentasi/justifikasi.

Simpan seluruh threshold-performance table agar keputusan dapat ditelusuri.

# 56. Recall Interpretation

Recall / Sensitivity:

```text
TP / (TP + FN)
```

Meaning:

> among all true DM patients, how many are detected by the model?

Because screening emphasizes avoiding missed DM cases, false negatives are important.

But avoid maximizing Recall without considering Precision/Specificity.

Example invalid model:

```text
predict everyone as DM
Recall = 100%
```

but unusable.

---

# 57. Specificity

Add Specificity explicitly if not currently implemented:

```text
Specificity = TN / (TN + FP)
```

Required because lowering threshold to increase Recall can create many false positives.

Threshold selection should show the Recall-Specificity tradeoff.

---

# 58. F2 Score

Add F2:

```text
F2 = weighted harmonic mean
with Recall weighted more heavily than Precision
```

Can be used as one candidate criterion for screening threshold selection.

Do not use F2 as replacement for PR-AUC in algorithm selection.

---

# 59. PR-AUC vs Threshold Metrics

Remember:

```text
PR-AUC
```

is threshold-independent.

Metrics such as:

```text
Recall
Precision
Specificity
F1
F2
```

depend on threshold.

Therefore:

```text
Model selection → primarily PR-AUC
Threshold selection → Recall/Specificity/F2 tradeoff
```

Keep these stages separate.

# 70. Core Methodological Rule

The most important rule of this entire refactor:

> Development data is where decisions are made.
>
> Final test data is where already-made decisions are evaluated.

Do not use final test performance to decide:

```text

which algorithm
which imbalance strategy
which hyperparameters
which threshold
```

The test set must remain independent until the final evaluation.

```

Kalau dikasih ke Codex, brief ini sudah cukup detail untuk membuat dia paham **bukan hanya “hapus kolom ini”**, tetapi juga *kenapa* perubahan dilakukan dan bagaimana pipeline final yang kita mau.
```
